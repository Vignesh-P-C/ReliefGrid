# Seed source-to-table mapping

This crosswalk records what the project's seed SQL and data fixtures actually
claim. It distinguishes source observations from editorial choices and
simulation values; a source mentioning a place or need does not make a
synthetic person-level request a real record.

## Scope and audit rules

- The SQL seed is [`seed.sql`](seed.sql). Deterministic PostgreSQL-ready CSVs
  are described in [`datasets/README.md`](datasets/README.md) and generated by
  [`datasets/generate_datasets.js`](datasets/generate_datasets.js).
- Database-generated primary keys are assigned by `SERIAL` unless a CSV import
  explicitly supplies an ID. A key is not a source field.
- Historical source counts refer to their stated observation/publication date;
  they are not live values. The repository does not record the date a person
  downloaded most source pages. Where that date is unknown, it is stated as
  unknown instead of being inferred from a file timestamp.
- No source is claimed to grant a license unless the evidence below says so.
  Government pages/publications and news articles have no reuse permission
  established in this repository. The Munro dataset author states CC BY 4.0;
  its files are not included or imported.
- Coordinates are decimal latitude/longitude (EPSG:4326 convention); camp and
  request coordinates are approximate locality/admin-center points, not
  surveyed camp or requester positions. No coordinate precision implies
  location accuracy.

## Seed SQL batches

### Historical `Disaster_Events` rows 1–13

Source batch: SRC-001, with K-08/K-09 supplying extra Kerala context.
The source's event/disaster description, disaster type, region(s), year, and
death toll (when available) inform the rows. The source PDF is not locally
bundled, and the original source columns/row identifiers were not preserved in
the seed, so the specific row-to-page references remain a citation gap.

| Destination | Source field / transformation |
|---|---|
| `name` | Built from the source's event label/type/year into the seed's display name. Wording and punctuation are normalized; this is not a direct verbatim field. |
| `type` | Disaster type from the table, with minor display normalization. |
| `region` | Source region(s), shortened where needed to fit `VARCHAR(100)` (the 1993 entry is explicitly abbreviated in SQL; full context is in `DATA_SOURCES.md`). |
| `severity` | 1–5 editorial bucket, roughly informed by deaths where reported. This is not a CSO field and no reproducible bucket thresholds are documented; treat as DERIVED/editorial, not measured severity. |
| `start_date` | SQL requires a full date while source often gives only year. A year-only record is represented as January 1 (a placeholder, not an observed start date); selected events use a separately reported date, with Kerala's 2018-08-08 supported by K-08. Other exact dates are described in SQL as widely reported, but row-level references are not supplied. The date for each seed row should therefore be read with that limitation. |
| `end_date` | Not supplied by the source mapping or seed insert; omitted and left NULL. |

Units: death tolls are people/deaths as reported, but are comments/context only
and are not stored in the current `Disaster_Events` schema. Deduplication:
these 13 selected event rows are manually curated; no source record ID or
automated deduplication key is preserved. The 2019 row is an annual event
summary, not a precisely dated incident.

### Synthetic `Disaster_Events` rows 14–15

`Cauvery Flood 2026 (fabricated)` and `Nilgiris Landslide 2026 (fabricated)`
are wholly synthetic (`name`, `type`, `region`, `severity`, and `start_date`)
and exist for cross-event query demonstrations. There is no source batch,
source URL, or reuse question. Database `event_id` values are generated keys.

### Real-context `Shelters` rows 1–5

Sources: K-03 through K-06. These records combine source-reported
headcounts with modeled shelter rows. Aggregate district rows are not
individual physical camps.

| `Shelters` destination field | Source field / transformation |
|---|---|
| `event_id` | Foreign key to the manually seeded `Kerala Floods 2018` event; not present in the articles. |
| `name` | Institution/district and aggregate description assembled from the report. Counts of camps are retained in some names (64 and 87); there is no separate camp-count column. |
| `address` | General locality/district label, not a geocoded street address from the source. |
| `latitude`, `longitude` | Approximate town or district-center decimal-degree coordinates. Not source-reported camp coordinates. |
| `capacity_occupied` | Reported people sheltered: ~2,800 Kalady, 9,000 Ernakulam, 3,521 Idukki, 6,111 Wayanad. These are headcounts at the reporting time, not current values. Alappuzha's source reports 125,000 people; seed stores 118,000 as occupied to leave headroom, so that occupied value is modeled and not source-reported. |
| `capacity_total` | Kalady 3,000, Ernakulam 9,500, Idukki 3,700, and Wayanad 6,400 are modeled headcount-plus-buffer values. Alappuzha 125,000 is the source's reported people-in-camps figure copied into a field named total capacity; it is not a designed maximum. |
| `contact_number` | Synthetic test phone values; not sourced. |
| `coordinator_id` | Foreign key to synthetic test users; not a real historical assignment. |
| `status` | `active` is a schema/demo value; these are historical observations and not proof of operational status. |
| `shelter_id` | Database-generated key; not sourced. |

The source measures are people and, where explicitly available, number of
camps. No time-series or de-duplication method exists across these differently
dated reports. The rows must not be summed as a simultaneous snapshot. The
repository does not retain a precise publication timestamp for every report.

### Synthetic `Shelters` rows 6–8 and 23–54

All attributes in these rows (names, event association, address, coordinates,
capacities, status, test contact/coordinator references) are fabricated
fixtures. They have no source fields, units from a source, or source-driven
deduplication. They support demonstration and scale tests only. IDs are
database keys where generated; deterministic CSV fixture IDs may be explicit.

### Kerala district snapshot: source CSV and schema-ready shelter fixture

Source: SRC-002. The bundled source extract contains 14 districts for the
single snapshot date 2018-08-20. It is separate from the five seed SQL shelter
rows; importing it creates district aggregates, not individual shelters.

| Source CSV field | Destination / handling |
|---|---|
| `snapshot_date` | Used as historical context in generated row naming/metadata; no matching observation-date column exists in `Shelters`. |
| `district` | `Shelters.name` aggregate label and `address` district label. |
| `relief_camp_count` | Included in the generated `name` text; there is no dedicated destination column, so it is not queryable as a number after import. |
| `people_in_camps` | `capacity_occupied`, preserving people as an integer headcount for the snapshot. |

Generated fields: `event_id` links to the Kerala event; `latitude`/`longitude`
are approximate district administrative-center coordinates; `capacity_total`
adds a modeled buffer to the reported occupants; `status` is
`historical_snapshot`. `shelter_id` is a fixture/import key. These are not
publicly reported camp capacities or current availability. The source CSV is
a transcription, not an archived copy of the original web page; independent
row-level comparison and retrieval date are not logged.

### `Aid_Requests` rows 1–5: illustrative requests, not source records

Context sources: K-05 through K-07 and K-10. Reports establish that
the localities were affected and describe response needs; none supplies these
individual requests. In particular SRC-010 lacks a preserved URL.

| `Aid_Requests` destination field | Source field / transformation |
|---|---|
| `event_id` | Foreign key to the seeded Kerala event; attached by project authors. |
| `requester_name`, `phone` | Invented placeholders/test numbers. No real requester is represented. |
| `latitude`, `longitude` | Approximate locality coordinates, not precise need locations or source-provided request coordinates. |
| `request_type` | Selected by authors from broad reporting context (`rescue`, `food`, `shelter`, `water`); not a verbatim individual request category. |
| `num_people`, `urgency_level` | Invented scenario values; no source count/urgency field maps to them. |
| `status` | `pending` is a demo workflow state, not a status reported by the articles. |
| `created_at` | In `seed.sql`, omitted from the insert and supplied by the schema's `now()` default at load time; it is not the 2018 request time. The deterministic CSV fixture supplies generated 2026 timestamps, also synthetic. |
| `request_id` | Database-generated key; not sourced. |

These five rows are synthetic example requests anchored to real place/need
context. They must not be interpreted as historical victim-level data. No
deduplication is meaningful or performed against article mentions.

### Synthetic `Aid_Requests` rows 6–2508 and allocation fixtures

Seed SQL's three requests for synthetic events and the additional generated
scale requests (IDs 9–2508 in CSV fixtures) are FABRICATED. Fields including requester, phone, location, request type, people,
urgency, and status are simulation values. The generator uses fixed seed
`20261016`; request rows 9–508 are linked to 500 synthetic allocations, while
509–2508 remain pending. Allocation quantities and timestamps are synthetic.
`Allocations.allocated_at` is supplied by the schema default where omitted.
These deterministic records do not claim to describe real operations.

### Other operational seed and fixture batches

No public source provides operational records for this historical event in
ReliefGrid's own system. The following are fabricated test data, not sourced
observations:

| Batch/table | Fields and notes |
|---|---|
| `Users` | Names, phones, emails, role, and placeholder password hash are test identities; no personal source data. Seed SQL inserts 4. Deterministic CSV fixtures may include more. |
| `Volunteers` | User link, skills, availability are invented operational values. |
| `Volunteer_Tasks` | Shelter/volunteer links, task text, parent hierarchy, status, priority are demo workflow values. |
| `Supply_Categories` | Category labels are application taxonomy, not historical source records. |
| `Supplies` | Items, quantities, units, thresholds, and shelter/category links are simulation stock. The dataset notes that balances reflect deductions for the 500 synthetic allocation fixture rows. |
| `Shelter_Capacity_Log` | Synthetic time-series snapshots; `logged_at` values are generated fixtures, not historical measurements. |
| `Allocations` | No `INSERT INTO Allocations` batch exists in `seed.sql`; the deterministic CSV fixture contains 500 fabricated transaction rows. |

Primary and foreign keys for these batches are generated or deterministic
fixture relationships, not source identifiers. Units (packets, bottles, kits,
pieces, people, and allocation quantity) are chosen for the simulation; they
are not standardized across categories and should not be added across unlike
items.

## Known audit gaps and schema limits

1. The exact EnviStats source page/table row for each event is not preserved;
   selected dates beyond the cited Kerala date need row-level citations.
2. Severity has no documented bucket thresholds. It is an editorial field and
   should not be presented as an objective source measurement.
3. `Shelters` conflates reported occupants with capacity semantics, especially
   Alappuzha; source date and camp count have no typed destination columns.
4. Real-context shelter/request coordinates are approximate. The schema has no
   coordinate provenance/accuracy field.
5. Aid-request stories support localities and broad need context only. The
   records' individual details are synthetic, and the Ranni article URL needs
   to be restored before that row has a fully traceable citation.
6. Source retrieval dates and complete reuse/license review are not recorded
   for most web reports. No reuse permission should be inferred from citation
   alone.
7. There is no persisted source-record key or formal deduplication process;
   historical rows were manually selected and curated.

These limitations are explicit so future contributors can improve the source
record without mistaking simulated operational values for observed data.
